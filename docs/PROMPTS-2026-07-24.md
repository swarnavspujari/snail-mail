## 1 — Split Inbox v2: per-account, real query language, sync-time classification

**Model: Claude Fable 5 · effort `xhigh`.** New query-language subsystem + schema migration +
cross-language dedup + background reclassification — ambiguous, cross-cutting, and the current
code has two divergent matchers to unify. Exactly Fable-class work.

Prompt:

> I'm reworking Split Inbox in Snail Mail (Superhuman-style Tauri email client) because as
> shipped it fails all three of its jobs: splits leak across accounts, they never organize
> existing or incoming mail, and a Superhuman-style definition like
> `from:thriftytraveler.com OR from:thepointsguy.com` silently matches nothing. Root-cause
> research with file:line evidence is in `docs/RESEARCH-2026-07-24.md` §1 — read it first; don't
> re-derive it. The short version: definitions are a global array in the settings blob with no
> account id; membership is a render-time substring filter over at most the newest 500 inbox
> threads, computed by `assignSplit` which lives in `src/lib/mock.ts` and is duplicated
> (divergently) in Rust; and the Definition field is a literal `includes()` needle — there is no
> parser, even though `src-tauri/src/search.rs::parse_deterministic` already parses Gmail
> operators for search.
>
> Build, in order:
> 1. **One query language, one matcher, in Rust.** Extend `parse_deterministic` into a boolean
>    AST: `from:` / `to:` / `subject:` / `label:`, quoted phrases, AND / OR / parentheses, and
>    bare-domain semantics (`from:thriftytraveler.com` matches any address whose domain is that
>    or a subdomain of it — match the address, not the display-name string). The acceptance
>    test is the exact query above classifying correctly. Delete the TS `assignSplit`; the front
>    end must not evaluate membership at all.
> 2. **Sync-time classification, persisted.** Compute each thread's split at
>    upsert/refetch time in Rust and store it on the thread row; run a background
>    reclassification pass (chunked, off the main thread, using the existing crawl-beat pattern)
>    whenever definitions change. Tab counts come from SQL. This is what makes splits cover the
>    whole mailbox instead of the newest 500, and makes `bulk_archive` agree with the UI.
> 3. **Data model:** each split gains `accountId: string | null` (null = all accounts — migrate
>    existing splits to null), a user-controlled order (custom splits default *above* the
>    built-in Important so they can win), and an "also show in Important/Other" flag per split
>    (a thread's home split is exclusive; the flag additionally surfaces it there, Superhuman
>    semantics). Keep `to:` honest: recipient addresses need to reach the thread model at sync
>    (`participants` is currently senders-only). Stop stripping `CATEGORY_*` labels at sync so
>    category-based splits work.
> 4. **Settings UI:** the Definition becomes a single query input that round-trips exactly what
>    it displays (today it *shows* `from:"…" OR from:"…"` syntax it can't parse — that's the
>    trap the owner fell into). Parse on input, show a friendly error for an unparseable query
>    and a live match-count preview for a valid one, allow reorder, edit (today it's
>    delete-and-recreate), and an account picker. Reconcile `activeSplitId` when a split is
>    deleted (today it dangles and fakes inbox-zero).
> 5. **Migration + parity:** migrate the persisted settings blob (old `rules[]`/`op` → query
>    string is a mechanical mapping); mirror new/changed IPC in both mock backends; add tests —
>    parser cases (the acceptance query, parens, quoted, domain vs display-name), a
>    classification test in Rust, and a settings-migration test. There are currently zero split
>    tests in either language.
>
> Constraints: don't write anything to Gmail (no labels/filters — splits stay app-local like
> Superhuman's); don't redesign the whole settings screen (that's a separate track); no other
> refactors. Verify in the browser demo and with `cargo check` + the new tests before claiming
> done, and point at the results. If a step turns out riskier than it looks, say so with a
> recommendation rather than pushing through.

## 2 — Account removal, storage, and grant health

**Model: Claude Fable 5 · effort `xhigh`.** Concurrency + schema + failure-mode work on the most
dangerous path in the app (destructive, involves the OS keychain and Google-side revocation),
with a measured performance cliff (quadratic FTS deletes) that a naive fix would keep.

**Owner decision 2026-07-24: build per-account database files, not the in-place fix.**

Prompt:

> I'm re-architecting mail storage in Snail Mail (Superhuman-style Tauri email client) to
> **one SQLite file per account**, because the shipped design — every account in one
> `fission.db` behind one mutex — makes account removal a minutes-long purge that froze the
> app (v0.22 chunked it; the structure remains), leaves a 5 GB file that never shrinks, and
> lets one account's data operations stall every other account's UI. With per-account files,
> removing an account is closing a connection and deleting a file. Root-cause research with
> file:line evidence: `docs/RESEARCH-2026-07-24.md` §2 — read it first; it maps every table,
> every kv key, the keychain entries, and the exact main-thread blocking mechanics.
>
> Deliver in three phases, each verified before the next:
> 1. **Per-account storage.** Layout: a small global db (settings blob, accounts registry,
>    streaks, app-wide kv) plus `accounts/<id>.db` per account holding everything
>    account-scoped — threads, messages, attachments, `mail_fts`, `mail_vec`/`vec_meta`,
>    labels, contacts, people_contacts, events, drafts, outbox, and the per-account kv keys
>    (`history:`/`crawl:`/`threads_total:`/`profile:`/`sendas:`/`granted_scopes:`/
>    `invite_miss:`). Replace `AppState.db` with a registry (global conn + per-account conns);
>    convert the synchronous DB-touching commands to async so nothing runs on the main thread
>    (that main-thread coupling is a root cause independent of file layout). Audit which
>    queries are genuinely cross-account — most (list_threads, search) already resolve the
>    active account; fan out and merge only where a feature truly spans accounts (e.g.
>    `search_all` ranking, contact aggregation), and say which those are. **Migration:** on
>    first boot, move each account out of the legacy `fission.db` via `ATTACH` +
>    `INSERT INTO … SELECT` per table (chunked, backgrounded, progress-visible, resumable),
>    keep `fission.db` renamed `.bak` until every account verifies (row-count checks), then
>    delete it. A killed migration must resume, not corrupt.
> 2. **Instant, honest removal.** `disconnect_account` marks the account `removing` in the
>    registry, revokes best-effort with a short timeout, returns immediately; a background
>    task closes the connection, deletes the db + `-wal`/`-shm`, sweeps that account's
>    attachment-cache files, keychain entries, `settings.signatures[email]`, and the
>    in-memory `labelCache`/`threadCache` (they currently serve removed-account mail from
>    memory). Idempotent and double-click safe; boot sweep deletes any account file not in
>    the registry. UI: confirm step, "Removing <email>…" state, error path. Fix the legacy
>    shared `gmail:refresh_token` keychain entry so one account's disconnect can't delete
>    another's only token. Reconnect-for-scopes must stop purging mail — re-consent in place.
> 3. **Dead grants visible and cheap to fix.** Classify auth failure everywhere sync can fail
>    (the boot reconcile still swallows errors; `sync_now`, `resync_account`, calendar,
>    people, crawl, outbox never classify), retry a 401 once through a token refresh so a
>    Google-side revoke is detected in seconds instead of up to an hour, and emit an
>    `accounts:updated` event the settings store subscribes to. Surface: a persistent
>    per-account "Reconnect" banner/CTA gated on `connected` (not on scopes), an accurate
>    header dot, and stop destroying queued outbox mail when a grant is dead (park it, resume
>    on reconnect — today it's silently deleted after 5 attempts).
>
> Constraints: schema inside each account file stays as close to today's as possible (don't
> redesign tables while relocating them); don't touch the sync algorithm; no unrequested
> refactors. Mirror IPC changes in both mock backends. Tests: migration round-trip on a
> seeded multi-account db (row counts + spot checks), removal idempotency, resume-after-kill,
> and `is_auth_revoked` classification. Measure and report: disconnect wall-time before/after
> on a large seeded db, and app responsiveness (a `list_threads` call) during migration.
> Before claiming any phase done, point at the tool output that proves it; report failures
> plainly. This is the riskiest change in the pack — if a phase looks wrong mid-flight, stop
> and say so with a recommendation.

## 3 — Live sync activity indicator

**Model: Claude Opus 4.8 · effort `high`.** The research fully specifies the design; this is
precise event-plumbing + a small UI, well inside Opus territory.

Prompt:

> I'm adding a live download indicator to Snail Mail (Superhuman-style Tauri email client): a
> subtle counter — "Downloading 17 of 30…" — whenever the Gmail API is being hit, alongside the
> existing "Downloading mail history… N%" footer (which measures long-term crawl completeness
> and stays). Research: `docs/RESEARCH-2026-07-24.md` §3. The counts already exist in Rust and
> are discarded: `fetch_streaming` (`src-tauri/src/mail/sync.rs:295-318`) knows the exact
> denominator and loop index but the callback is a zero-arg `Fn()`; the incremental path knows
> `affected.len()` and never reports at all; crawl/embed beats print to stderr. Every Gmail
> round-trip is one `threads.get`, so "X of N" maps 1:1 onto requests.
>
> Build:
> 1. Widen the sync progress callback to carry `{account, stage, done, total}` (stages:
>    reconcile-inbox, reconcile-rest, incremental, crawl, resync). Emit a new `sync:activity`
>    event, **time-coalesced in Rust to at most ~4/s**, always emitting the terminal tick of a
>    pass. Wire it through every currently-silent path: the 30s incremental tick, boot
>    reconcile, `sync_now`, `resync_account`, post-crawl reconciles, and `load_older`. Add a
>    pull command `get_sync_activity` so a late-mounting UI can't miss an in-flight pass.
> 2. Front end: a small transient pill (leaf component subscribed directly to the event — do
>    NOT subscribe at the App root; `sync:progress` already re-renders the whole tree per event,
>    don't repeat that) that appears when a pass reports more than ~5 items or lasts >1 s,
>    counts up live, and fades on completion. It must also show during onboarding's first sync,
>    where the biggest download of all currently has zero feedback.
> 3. While in the plumbing, fix three adjacent correctness bugs from the research: the footer's
>    numerator/denominator populations don't match (clamped to 99% to hide it) — count only
>    non-hidden threads and derive the total from the crawl's own listing; `resync_account`
>    doesn't reset the `crawl:` cursor so Repair Mail re-downloads everything with the footer
>    suppressed; and `emit_sync_progress`'s per-beat `COUNT(*)` needs the
>    `threads(account_id)` index if task #2 hasn't landed it yet.
> 4. Mock parity: give the browser demo a real simulation of `sync:activity` (per-item ticks,
>    not one fake climb) so the pill is demoable, and keep `mock.syncNow()` honest.
>
> Don't add per-message granularity (thread-level is what the API does), don't build a sync
>-history UI, and don't touch the footer's visual design. Verify in the browser demo and with
> `cargo check`; show the pill appearing for a simulated 30-thread pass before claiming done.

## 5 — Demo account removal + zero-account state

**Model: Claude Opus 4.8 · effort `xhigh`.** The seam is fully mapped, but the task spans Vite
build config, Rust boot paths, a data migration for existing installs, and a new UI state — high
end of Opus.

Prompt:

> I'm removing the demo account from Snail Mail's desktop builds — it must not ship in the
> product — while keeping the browser demo (`npm run dev`) fully working. The research
> (`docs/RESEARCH-2026-07-24.md` §4.2) maps the seam; the critical fact is that demo mode is
> currently the app's **zero-account state**: `store::get_accounts` falls back to two fake
> accounts, fixtures are seeded into the user's real SQLite DB on first boot, and disconnecting
> your last real account deliberately re-seeds demo. So this is five changes, not one:
> 1. **A real zero-account state.** Desktop with no connected accounts renders the onboarding /
>    connect screen — not a fake inbox. Disconnecting the last account lands there too. No demo
>    accounts in the switcher or Settings on desktop, ever.
> 2. **Build-time split.** The mock backend is a static import (`src/lib/ipc.ts:40`) selected by
>    a runtime `isTauri` check, so it ships in the desktop bundle (~43 KB min). Make the split
>    build-time (dynamic import behind a Vite define / separate entry) so desktop bundles
>    exclude `mock.ts`/`mock-data.ts` entirely and the web demo keeps them.
> 3. **Rust side:** desktop builds never seed fixtures (`seed_if_empty` and the demo fallbacks
>    in `get_accounts`/`disconnect_account`/boot) — gate with a cargo feature or remove and keep
>    the Rust demo paths only where the browser-demo parity tests need them. Keep `is_mock_id`
>    as a legacy-DB safety net for now.
> 4. **Migration for existing installs:** on update, purge previously-seeded demo threads/
>    messages/vectors and the demo account entries from real DBs (reuse the account-purge path;
>    it's the `t-`/`t2-` id shapes plus the two `@fission.local` accounts).
> 5. **Onboarding:** remove "Explore the demo first" from desktop; keep it on web.
> Constraints: the browser demo must remain byte-for-byte as capable as today — it's the test
> bed; don't refactor the mock itself; don't change onboarding beyond the CTA. Verify: desktop
> bundle no longer contains mock-data strings (check the built assets), `npm run dev` still
> boots the full demo, fresh-install desktop flow lands on connect, and the migration removes
> seeded rows from a copied DB. Point at each verification result before claiming done.

## 7 — Taskbar unread badge

counts unread in the Important (primary) split — so RUN THIS AFTER PROMPT 1 (Split Inbox v2)

Prompt:

> Add a Windows taskbar unread badge to Snail Mail (Tauri 2.11.5): the taskbar icon shows the
> count of unread conversations in the **Important (primary) split**, summed across connected
> accounts — like Superhuman's dock badge. Research: `docs/RESEARCH-2026-07-24.md` §5.4.
> Prerequisite: Split Inbox v2 has landed, so thread rows carry a materialized split id in
> SQL — verify that first and stop with a clear message if it hasn't. Facts you need: the

> filled circle + centered count (cap display at "9+") at 32×32.
>
> Implementation: a `refresh_badge(app)` in Rust that counts unread, in-inbox, non-hidden
> threads whose materialized split is the primary/Important split, summed across accounts,
> sets the overlay (or clears it with `None` at zero), and is called wherever `mail:updated`
> is emitted — hook the emit funnel, not individual call sites, so it can never go stale.
> Also refresh on boot after the store opens, and clear it when the last account disconnects.
> Add a `settings.showBadge` boolean (default true) with a palette toggle command; the
> settings redesign will re-home the control.
>
> Mock parity: browser demo has no taskbar — no-op cleanly. Verify with `cargo check`, a unit
> test for the RGBA digit rendering (pure function), and a manual desktop check if a dev build

## 9 — Clean uninstall

**Model: Claude Opus 4.8 · effort `high`.** Installer + lifecycle work with sharp constraints
(update-mode guard, credential store), fully specified by the research.

Prompt:

> Make Snail Mail's Windows uninstall actually clean. Research:
> `docs/RESEARCH-2026-07-24.md` §5.5 — the facts: Tauri v2 has no `deleteAppDataOnUninstall`;
> the stock NSIS template deletes app data only behind an unchecked-by-default checkbox whose
> scope is the two identifier dirs + vendor registry keys; **Credential Manager entries
> (live Google refresh tokens, AI keys) survive uninstall unconditionally**; legacy-brand
> orphans (`com.zenbox.mail` dirs, `FissionMail`/`ZenBoxMail` credential entries, old registry
> keys) are never cleaned; and `dev-secrets.exe` (a keychain-writing dev helper) ships in the
> installed app dir.
>
> Build:
> 1. **In-app "Erase all local data"** (Settings → Account area for now): revokes + deletes
>    every keychain entry across all three service names (`SnailMail`, `FissionMail`,
>    `ZenBoxMail`), closes the DB and deletes `fission.db*`, the `models/` and `attachments/`
>    dirs, and resets to the zero-account state. This is the only reliable way to reach the
>    credential store.
